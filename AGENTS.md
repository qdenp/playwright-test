# AGENTS.md — правила работы с тестами в этом репозитории

Эти правила применяются автоматически во всех сессиях. Их нарушение = неполноценная работа.

---

## 1. Что за проект

`playwright-tests/` — e2e-тесты [SauceDemo](https://www.saucedemo.com, который был скопирован в https://qdenp.github.io/playwright-test/), написанные **пять раз**:

| Реализация | Путь | Фреймворк | Команда запуска |
|---|---|---|---|
| TypeScript (эталонная) | `playwright-tests/typescript/` | Playwright Test | `npx playwright test` |
| JavaScript | `playwright-tests/js/` | Playwright Test | `npx playwright test` |
| Python | `playwright-tests/python/` | pytest + pytest-playwright | `pytest` |
| Java | `playwright-tests/java/` | Selenium WebDriver + JUnit 5 | `mvn test` |
| C# | `playwright-tests/csharp/` | Playwright .NET + xUnit | `dotnet test` |

Пять реализаций существуют **намеренно**: это практика на разных стеках и портфолио.
Ни одну из них нельзя удалять, сливать в одну, переводить в «legacy» или объявлять
устаревшей. Задача — не сокращение числа реализаций, а их паритет.

Наборы покрывают **один и тот же** список сценариев (сейчас по 29 тестовых файлов
в каждой, файлы `NN-topic`). TypeScript считается эталоном: правку вносишь сначала туда,
затем зеркалишь в JS, Python, Java и C#. Если правка осознанно не зеркализируется — расхождение
фиксируется в `.kilo/skills/playwright-tests/SKILL.md` с причиной, а не «забывается».

Артефакты (`playwright-report/`, `test-results/`, `reports/`, `__pycache__/`, `.pytest_cache/`)
не редактировать вручную и не коммитить.

## 2. Проверка перед тем как считать задачу выполненной

Обязательны оба шага для затронутых реализаций:

```powershell
# TypeScript / JavaScript
npx tsc --noEmit
npx playwright test --project=chromium --reporter=line

# Python (флаги уже заданы в pytest.ini, добавлять --reporter=line НЕ надо:
# в проекте pytest-html, а не pytest-reporter)
pytest

# Java (Maven установлен в C:\tools\apache-maven-3.9.9)
C:\tools\apache-maven-3.9.9\bin\mvn.cmd test

# C#
dotnet test
```

Ранее `npx tsc --noEmit` в `typescript/` падал на `16-add-remove-all.spec.ts` (невалидный
`{ timeout }` в третьем аргументе `test()`) и на `24-about-page.spec.ts` (`test.skip()`
со строкой вместо колбэка). Оба исправлены — на момент 2026-10-12 проверка чистая.

Если снова увидишь ошибки типов — почини до того, как считать задачу выполненной:
в CI джоба `lint` падает на любой ошибке `tsc`.

**Никогда не сообщай «тесты проходят», не запустив их.**

## 3. Обязательные правила написания тестов

### 3.1 Web-first ассерты — единственно допустимый способ
```ts
// ПРАВИЛЬНО — авто-ретрай, ждёт условие
await expect(inventoryPage.products).toHaveCount(6);
await expect(cartPage.cartBadgeText).toHaveText("2");
await expect(page).toHaveURL(/inventory\.html/);

// НЕПРАВИЛЬНО — одна попытка прочитать DOM, без ретрая
expect(await inventoryPage.getProductCount()).toBe(6);
const prices = await inventoryPage.getAllProductPrices();
expect(prices[1]).toBeGreaterThanOrEqual(prices[0]);
```

### 3.2 Запрещённые анти-паттерны
- `page.waitForTimeout(...)` / `wait_for_timeout(...)` — вместо этого `expect(...).toHaveCount()`,
  `locator.waitFor({ state: "detached" })` или ожидание навигации.
- `try { ... } catch { break; }` / `except: pass` — глушение ошибок. Реальный сбой должен падать.
- Замеры производительности через `Date.now()` / `time.time()` без warmup и без усреднения.
- Логин «на всякий случай» в `beforeEach`/авто-фикстуре — только если тест реально в нём нуждается.

### 3.3 У каждого теста должна быть проверка
Тест без `expect` / без `assert` — это не тест. Скриншот сам по себе ничего не проверяет;
скриншот допустим только вместе с ассертами или через `toHaveScreenshot`.

### 3.4 Дисциплина Page Object
- В спеках **нет** `page.locator(...)`, `page.get_by_text(...)` — только методы и свойства PO.
- Если нужного метода в PO нет — сначала добавь его в PO (и в четыре другие реализации), потом
  используй в тесте.
- Локаторы живут в PO один раз. Совпадающие локаторы под разными именами — мёртвый код:
  удаляй.
- Не дублируй бизнес-логику в PO (`get_login_params`, `get_all_credentials` — это данные,
  они живут в `config.ts` / `conftest.py`, не в PO).

### 3.5 Селекторы
- Предпочтительно `[data-test="..."]` — стабилен к вёрстке.
- Цепочки вида `.btn.btn_primary.btn_small.btn_inventory` — только если `data-test` нет.
- `getByText("...")` / `:has-text("...")` — избегать: матчит несколько узлов. Для кнопок
  используй `getByRole("button", { name: "..." })`.
- Строка с `${variable}` внутри локатора (динамический `:has-text`) — не использовать без
  обязательного экранирования и гарантии уникальности.

### 3.6 Ассерты по деньгам и количествам
- Цены, subtotal, tax и total проверять **точно**, а не «товар добавлен».
- Обязательно проверять итоговую сумму заказа: item total → tax → total.
- Счётчики — точным числом (`toBe(6)`), не `toBeTruthy()` / `toBeGreaterThan(0)`,
  когда известен эталон.

### 3.7 Данные и конфигурация
- Все таймауты — из `config.ts` (`timeouts`) / `constants.py` (`DEFAULT_TIMEOUT` и др.).
  Хардкод `timeout: 10000` в тестах и PO запрещён.
- Ожидаемое число товаров (`6`) — именованная константа, не магическое число.
- Credentials — только из env:

| Переменная | Где используется | Формат |
|---|---|---|
| `SAUCE_DEMO_USERNAME` / `SAUCE_DEMO_PASSWORD` | TS | по одной на переменную |
| `SAUCE_DEMO_PASSWORDS` | Py | `user:pass,user2:pass2` |
| `SAUCE_DEMO_BASE_URL` | Py | URL |

Никогда не коммить реальные пароли и `.env` с секретами. Python `.env` читается через
`os.getenv` — поддерживай схему единой.

### 3.8 Соглашения
- Импорт фикстур: выбери **один** канонический вариант (в этом проекте — `from "../fixtures"`,
  так как `moduleResolution: "node"`; оба варианта компилируются, но смешение запрещено).
- Названия тестов описывают **поведение и ожидаемый результат**, а не номер.
  Номер живёт **только** в префиксе имени файла `NN-topic.spec.ts` — в заголовках
  `test(...)`, в имени `test.describe(...)`, в `test.skip(...)` и в doc-комментариях
  номера быть не должно. Не используй префиксы вида `Тест 12: ` или `12 - `.
- Тесты не должны зависеть от порядка выполнения друг друга: каждый тест создаёт своё
  состояние самостоятельно (`fullyParallel: true`).
- Функциональность, которой в SauceDemo нет (API товаров, редактирование
  количества) — не тестировать. Если тест на это написан, он должен быть удалён или
  переписан на реальное поведение, с комментарием-обоснованием.
  Исключение — экспорт PDF: он **есть** (кнопка "Generate PDF order" на
  `checkout-complete.html`, проверено пробой 2026-10-13), тест `22-export-pdf`
  легитимен.

## 4. Известные особенности SauceDemo (учитывай всегда)

- **Нет API товаров.** Страницы рендерятся на сервере. `page.route` / перехват API для
  получения товаров бессмысленен. Для сетевых проверок используй `page.on('response')`
  на **своей** навигации, иначе массив будет пустым.
- **Количество товара в корзине не редактируется.** Проверяй отсутствие поля, а не его изменение.
- `performance_glitch_user` — намеренно медленный; высокие таймауты для него обязательны.
- `locked_out_user` — всегда получает ошибку «locked out».
- `About` ведёт на `saucelabs.com`, который отдаёт 403 — тест об этой странице должен быть
  `test.skip` с явным комментарием причины.
- Пустая корзина не содержит badge — `getCartBadgeCount()` обязан возвращать `0`, а не падать.

## 5. Как оформлять результат

- После правок: сначала факт запуска, потом список затронутых файлов с `file:line`.
- Если нашёл баг в существующих тестах — не «почини молча рядом»: зафиксируй находку
  и спроси, включать ли её в текущую задачу.
- Мёртвый код (неиспользуемые локаторы/методы в PO) удаляй сразу при правке файла.
- Крупные ревью сохраняй в `playwright-tests/` отдельным файлом с датой в имени,
  не перезаписывая предыдущие.
